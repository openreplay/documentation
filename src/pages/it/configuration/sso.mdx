Il Single-Sign-On (via SAML2) è disponibile solo con OpenReplay Enterprise Edition.

## Configurazione dell'Identity Provider (IDP)

Nella dashboard del tuo Identity Provider, crea una nuova app chiamata `openreplay` (puoi usare questa <a href="https://docs.openreplay.com/static/OpenReplay.png" target="_blank">icona</a>). Nella pagina di configurazione, imposta il valore seguente (sostituisci <code>{initialValues.domain}</code> con il valore corretto, ad esempio `https://openreplay.mycompany.com`):

| Variabile | Valore |
|----------|-------------|
| ACS URL (chiamato anche Single Sign On URL o Consumer URL) | <code><ORDynamicCode id="domain" initialValue={initialValues.domain} client:idle/>/api/sso/saml2/acs/</code> |
| Entity ID (chiamato anche Audience) | <code><ORDynamicCode id="domain" initialValue={initialValues.domain} client:idle/>/api/sso/saml2/metadata/</code> |
| Single Logout URL (chiamato anche SLO URL) | <code><ORDynamicCode id="domain" initialValue={initialValues.domain} client:idle/>/api/sso/saml2/sls/</code> (facoltativo) |
| Name ID (a volte è configurabile nella sezione 'Attribute Statements' o 'Parameters') | `Email` o `EmailAddress` o `urn:oasis:names:tc:SAML:1.1:nameid-format:emailAddress`, a seconda del tuo Identity Provider |
| SAML initiator | Impostalo su `Service Provider` (facoltativo) |

Nella sezione 'Attribute Statements' o 'Parameters', assicurati di definire i campi seguenti:

| Campo | Valore |
|----------|-------------|
| tenantKey | <code><ORDynamicCode id="tenantKey" initialValue={initialValues.tenantKey} client:idle/></code> il suo valore si trova nella Dashboard, in 'Preferences' > 'Account' (questo attributo non deve essere aggiunto se usi il nostro piano Cloud Dedicated) |
| firstName | `user.firstName` |
| lastName |  `user.lastName` |
| internalId | Internal ID o `user.email` (l'ID dell'utente nel tuo sistema di gestione delle identità) (facoltativo) |
| groups | Rappresenta il ruolo e i privilegi di amministratore dell'utente in OpenReplay; a seconda del tuo Identity Provider può essere `user.role` o `group`, ecc. (facoltativo, predefinito = `member` senza privilegi di amministratore). Per semplificare la gestione dei ruoli di OpenReplay dal lato dell'IdP, puoi creare un gruppo chiamato OpenReplay-admin con gli utenti che hanno privilegi di amministratore e un gruppo chiamato OpenReplay-member con gli utenti che hanno il ruolo 'member' |

A questo punto dovresti avere tutti i valori necessari per il passaggio/la sezione successiva.

## Configurazione di SSO (SAML2)

Se usi il nostro piano Cloud dedicated, vai alla [Console](https://console.openreplay.com), fai clic sull'istanza e imposta le variabili nella sezione SSO.

Altrimenti, se usi la nostra Enterprise Edition, esegui `openreplay -e`, decommenta e aggiorna le seguenti variabili d'ambiente nella sezione `chalice`:

| Variabile | Descrizione |
|----------|-------------|
| idp_entityId | L'`entityId` del tuo identity provider, indicato anche come `Issuer URL` |
| idp_sso_url | Il `singleSignOnService` del tuo identity provider, indicato anche come `SAML 2.0 Endpoint (HTTP)` |
| idp_x509cert | L'`x509cert`; deve essere una stringa su una sola riga, senza interruzioni di riga. Puoi usare <a href="https://www.samltool.com/format_x509cert.php" title="FORMATTA UN CERTIFICATO X509" target="_blank">questo strumento</a> per formattare il valore |
| idp_name | Il nome dell'identity provider (facoltativo) |
| idp_sls_url | Il `singleLogoutService` del tuo identity provider, indicato anche come `SLO Endpoint (HTTP)` (facoltativo) |
| enforce_SSO | Se impostato su `true`, tutte le connessioni con nome utente e password verranno bloccate (facoltativo, predefinito=`false`) |
| idp_group_prefixes | I prefissi dei nomi dei gruppi dell'IdP (facoltativo, predefinito=`OpenReplay-,or-`) |

Poi salva ed esci con `:wq` affinché le modifiche abbiano effetto:

## Certificato di OpenReplay

Questo passaggio è facoltativo: puoi aggiungere un certificato x509 per una maggiore sicurezza dell'SSO:

1. Esegui questo comando sul tuo server o su una macchina sicura (puoi modificare la durata di validità del certificato in base alle tue esigenze):
```bash
openssl req -x509 -nodes -days 365 -newkey rsa:2048 -keyout openreplay-sso.key -out openreplay-sso.crt
```
2. Sul tuo server, esegui `openreplay -e`
3. Nella sezione `chalice`, aggiungi le seguenti variabili d'ambiente:
- **sp_crt**: deve essere una stringa su una sola riga, senza interruzioni di riga, del file 'openreplay-sso.crt' generato (puoi usare <a href="https://www.samltool.com/format_x509cert.php" title="FORMATTA UN CERTIFICATO X509" target="_blank">questo strumento</a> per formattare il valore)
- **sp_key**: deve essere una stringa su una sola riga, senza interruzioni di riga, del file 'openreplay-sso.key' generato
4. Salva ed esci con `:wq` affinché le modifiche abbiano effetto
5. Aggiungi il file 'openreplay-sso.crt' generato alla configurazione dell'applicazione nel tuo Identity Provider

## Esempio con Okta

1. Accedi alla dashboard di amministrazione di Okta e vai su 'Applications' > 'Applications'
2. Premi 'Create new app integration', poi seleziona SAML 2.0 e premi 'Next'
3. Imposta 'App Name' su OpenReplay (puoi caricare questa <a href="https://docs.openreplay.com/static/OpenReplay.png" target="_blank">icona</a> per la tua applicazione), poi premi 'Next'
4. Imposta:
 - **Single sign on URL** su <code><ORDynamicCode id="domain" initialValue={initialValues.domain} client:idle/>/api/sso/saml2/acs/</code>
 - **Audience URI (SP Entity ID)** su <code><ORDynamicCode id="domain" initialValue={initialValues.domain} client:idle/>/api/sso/saml2/metadata/</code>
 - **Name ID format** su `EmailAddress`
5. Premi Next, seleziona 'This is an internal app that we have created', poi premi 'Finish'
6. Nella scheda Sign On, scorri verso il basso, premi 'Show legacy configuration', poi premi 'Edit'
7. Definisci i campi seguenti in 'Profile Attribute Statements':
 - **tenantKey**: formato `Basic` e imposta il valore su <code><ORDynamicCode id="tenantKey" initialValue={initialValues.tenantKey} client:idle/></code>, che si trova nella dashboard di OpenReplay in 'Preferences' > 'Account' (questo attributo non deve essere aggiunto se usi il nostro piano Cloud Dedicated)
 - **firstName**: formato `Basic` e imposta il valore su `user.firstName`
 - **lastName**: formato `Basic` e imposta il valore su `user.lastName`
 - **internalId**: formato `Basic` e imposta il valore su `user.email`
8. Definisci il campo seguente in 'Group Attribute Statement' (facoltativo):
 - **groups**: formato `Basic`, filtro `Match Regex`, valore `OpenReplay-*` (oppure puoi specificare un filtro e una regex diversi in base alle tue esigenze)
9. Premi 'save', scorri in alto a destra e premi 'View Setup Instructions' per vedere la tua configurazione SAML2

Se usi il nostro piano Cloud dedicated, vai alla [Console](https://console.openreplay.com), fai clic sull'istanza e imposta le variabili nella sezione SSO.

   - **idp_entityId**: Identity Provider Issuer
   - **idp_sso_url**: Identity Provider Single Sign-On URL
   - **idp_x509cert**: X.509 Certificate, deve essere una stringa su una sola riga, senza interruzioni di riga (puoi usare <a href="https://www.samltool.com/format_x509cert.php" title="FORMATTA UN CERTIFICATO X509" target="_blank">questo strumento</a> per formattare il valore)

## Provisioning SCIM (System for Cross-domain Identity Management)

Openreplay supporta il provisioning delle identità degli utenti nella Enterprise Edition.

Per l'integrazione con il servizio SCIM di Openreplay, basta abilitare il provisioning SCIM nella dashboard del tuo Identity Provider. Assicurati di impostare i valori seguenti per un'integrazione senza problemi:

| Variabile | Descrizione |
|----------|-------------|
| SCIM connector base URL | <code><ORDynamicCode id="domain" initialValue={initialValues.domain} client:idle/></code>/api/sso/scim/v2/ |
| User unique identifier field name | `email` |
| Support provisioning actions | Push new users, Push profile updates, Push groups |
| Authentication mode | OAuth2 |
| Access token endpoint | <code><ORDynamicCode id="domain" initialValue={initialValues.domain} client:idle/></code>/api/sso/scim/v2/token/ |
| Authorization endpoint | <code><ORDynamicCode id="domain" initialValue={initialValues.domain} client:idle/></code>/api/sso/scim/v2/authorize/ |
| Client id | <code><ORDynamicCode id="tenantKey" initialValue={initialValues.tenantKey} client:idle/></code> il suo valore si trova nella Dashboard, in 'Preferences' > 'Account' |
| Client secret | Il suo valore si ottiene eseguendo questa query nel tuo database Postgres: <code>SELECT tenant_secret FROM tenants WHERE tenant_key = '<code><ORDynamicCode id="tenantKey" initialValue={initialValues.tenantKey} client:idle/></code>';</code> |

Dopo aver impostato questi valori, segui le indicazioni della dashboard del tuo Identity Provider per testare l'integrazione e autorizzare l'applicazione.

[Facoltativo] Esegui `openreplay -e`, cerca `chalice/environment` e definisci la variabile `SCIM_ALLOWED_REDIRECT_HOSTS` con l'host (o gli host) del tuo IdP; per impostazione predefinita è `.okta.com`. Se non sei sicuro del tuo host o vuoi un valore più restrittivo, puoi provare ad autenticare il tuo IdP e cercare il valore stampato nei log di chalice.

### Esempio con Okta

Nella tua applicazione SAML 2.0, procedi come segue

#### Aggiungere il provisioning SCIM

1. Fai clic sulla scheda **General**
2. Nella sezione **App Settings**, fai clic su **Edit**
3. Nel campo **Provisioning**, seleziona **SCIM** e fai clic su **Save**

#### Scegliere le opzioni di provisioning

1. Fai clic sulla scheda **Provisioning**. Le impostazioni della connessione SCIM compaiono in **Settings > Integration**.
2. In **Settings > Integration**, fai clic su **Edit**.
3. Specifica la **SCIM connector base URL** e il nome del campo dell'identificatore univoco dei tuoi utenti indicati sopra.
4. In **Supported provisioning actions**, scegli le azioni di provisioning indicate sopra.
5. Imposta il menu a discesa **Authentication Mode** sul valore indicato sopra.
6. Imposta **Access token endpoint**, **Authorization endpoint**, **Client id** e **Client secret** come indicato sopra.
7. Fai clic su **Save**.
8. Fai clic su **Authenticate application**.
9. Nella scheda **Provisioning**, fai clic su **To App**.
10. Fai clic su **Edit**, abilita `Create Users`, `Update User Attributes`, `Deactivate Users` e salva le modifiche (assicurati che queste opzioni risultino selezionate dopo il salvataggio, altrimenti aggiorna la pagina e ripeti questo passaggio).
- Prima di iniziare il passaggio successivo, ti consigliamo di creare in Okta nuovi gruppi, chiamati `OpenReplay-admin`, in cui elenchi gli utenti con privilegi di amministratore in OpenReplay, e `OpenReplay-members`, in cui elenchi gli utenti con il ruolo `member` in OpenReplay, ...    
11. Vai alla scheda **Push Groups**, fai clic su **+ Push Groups** (per nome o per regola), seleziona il gruppo che vuoi inviare a OpenReplay e premi **save**
- A questo punto, i gruppi inviati rappresentano i ruoli e i privilegi di amministratore in OpenReplay e non contengono l'elenco degli utenti di cui è stato effettuato il provisioning per OpenReplay.
12. Vai alla scheda **Assignmets** e aggiungi gli utenti nel modo che preferisci (tramite persone o gruppi)

## Errori

### La risposta è stata ricevuta in http anziché in https

È un caso molto comune, dovuto all'assenza dell'header 'X-Forwarded-Proto' nella richiesta. Per risolvere, assicurati che il Load Balancer inoltri correttamente l'header al backend di OpenReplay, ed esegui `openreplay -e`; nella sezione `ingress-nginx > config`, decommenta la riga `use-forwarded-headers: true`.
